# DraftBoard `firebase` layer — independent audit

2026-09-28. Produced by an independent reviewer with no involvement in building
this, working read-only against both worktrees, measured against `SPEC.md`
(requirements) and `ARCHITECTURE.md` (proposal). Ranked by how deep the fault
sits. "Measured" means it was run; "inferred" means read and not executed.

Reproduced as delivered.

---

## F1 — The read budget makes the deployed build unusable on air, and the thing that was supposed to fix that does not exist

**What the fault is.** `ARCHITECTURE.md` §5 opens with "Reads are the scarce resource… **Nothing is read at startup that is not needed to draw the first screen**," and §6 answers the broadcast case with a relay. Neither holds. Every page load reads the whole player registry, the whole board, and then the whole board again.

**Evidence.**

- `src/utils/playerRegistry.js:35-47` — `openRegistry()`, in its own words: "This is the biggest collection in the app — **728 documents**." It is read (via `readyVia`, i.e. an `onSnapshot` initial set) on every load. The optimisation there was real — it removed a duplicate read — but 728 is the floor, not the ceiling.
- `src/data/draftStore.js:55` — `openDraft()` calls `readyVia(PLAYERS)`, and `src/hooks/useDraftState.js:398` keeps `repository.follow(PLAYERS, adopt)` open for the session.
- `src/data/boardEntries.js:90-93` + `src/hooks/useBoardRankings.js:205` — 328 entries for the active board; Scouting asks for all four (`boardsToOpen(true)`), which the comment itself prices at "1,312 documents."
- `src/hooks/usePlayerTags.js:111-125` — on opening Draft, `repository.invalidate(path)` then `repository.ready(path)`: **a second full 328-document read of the same board**, gated only on a client-clock stamp.
- Plus `seasons`, `authors`, `boards`, `draft_state`, `seasons/{id}/stages`, `seasons/{id}/charts/{stage}/rows|bands` × 2 stages, `seasons/{id}/setup`.

A first Draft load is ≈ **1,450 documents**; Scouting ≈ **2,100**. Against the free tier's 50,000 reads/day that is **roughly 25–35 page loads per day for the entire audience**, after which — §5's own words — "exceeding it stops the app for everybody until it resets."

On top of that, rules `get()`/`exists()` calls are billed reads, and this file makes many. `boardVisible(boardId)` (`firestore.rules:221-251`) costs up to six document accesses per entries read; writing one entry costs three (`boardExists` + `isExpert` + `boardNow`). **Measured** against the emulator, same 300-document batch, same client:

```
allow-all rules  : 300-entry batch committed in 5019ms
the app's rules  : 300-entry batch committed in 13371ms
```

≈28 ms of rules evaluation per written document — the rules cost 1.7× the write itself.

And §6's relay is not built. Grep finds no relay, no snapshot-plus-stream interface, nothing. Experts and viewers both connect straight to Firestore.

**Is the foundation sound?** **No — the adapter seam has to come out.** The interface is `load(path)` / `watch(path)`, whole-collection only (`src/data/firebaseAdapter.js:108-161`). §4 requires per-entry `touchedAt`, recorded deletions distinguishable from absence, and a "caught up to" moment that only advances on a fully successful fetch. **None of that is expressible through this interface** — there is no `since` parameter and the repository's cache is a whole-collection map replaced wholesale on every snapshot. The one changed-since marker that exists (`u`, `src/data/boardEntries.js:223-232`) has exactly one consumer, and its "delta" is invalidate-and-refetch-all-328.

**Cost now:** the shared build cannot be put in front of an audience. **Cost later:** every consumer above the seam is written against whole-collection reads, so adding deltas is a rewrite of the repository and every `ready`/`follow` call site, not an adapter change.

## F2 — No expert can write a single strength, weakness or note on any personal board in the shipped data. Verified.

**What the fault is.** Two independent answers to "whose voice is this": the app derives it from the *board*, the rules derive it from the *token*. They can only agree when `board.authorId` equals the writer's uid, which the shipped seed guarantees will never happen.

- `src/utils/evaluations.js:29-31` — `ownerIdFor(board) = board?.authorId ?? board?.id`
- `firestore.rules:198-201` — `ownsVoice(v) = ownsAuthor(v) || (boardExists(v) && ownsBoard(v))`, and `ownsAuthor(v) = isExpert() && v == request.auth.uid` (`:177-179`)
- `src/utils/boardRegistry.js:154-163` — the shipped boards get **placeholder** authors with opaque `a_…` ids and `@draftboard.local` addresses, deliberately never a uid.

So `ownerIdFor(b_dan)` is a placeholder id, which is neither the caller's uid nor a board id. **Measured** against the emulator with exactly the seeded shapes:

```
claim b_dan (ownerId = his uid):                           ALLOWED
write an ENTRY on the board he now owns:                   ALLOWED
write a REMARK in the board voice ownerIdFor() gives (a_1): REFUSED (permission-denied)
write a REMARK keyed by his OWN uid (what the rules expect): ALLOWED
write a REMARK in the consensus voice (= board id):        ALLOWED
```

**And it is unrepairable from inside the app.** The board `update` rule freezes `a` (`firestore.rules:479`); `authors` is `delete: if false` (`:387`) and `create` demands the id be your own uid (`:378-380`). Nothing in the app can change a board's author. The only exits are the Firebase console or deleting and recreating the board, which throws away its placements.

**What makes it worse than a permission error.** `repository.withPending` lays refused writes over the store's answer on every read (`src/data/repository.js:52-64`), and the queue outlives the tab (`QUEUE_KEY = 'pending_writes_v1'`). So the expert *sees* his notes on screen, indefinitely, while the database holds none — the state `discardPending`'s own comment calls "somebody being shown their own rejected copy of a board belonging to somebody else, for good" (`:729-745`). This is the shipped default for every personal board.

This breaks SPEC §3 (the player card, "every evaluation of that player, from every author") and §4 (the verification step's buttons for adding strengths, weaknesses and notes).

The rules suite has the blind spot in plain sight: `tests/rules/rules.test.js:188` — `it('refuse a voice belonging to no author and no board')` — asserts this refusal is *correct*, without noticing the shipped data produces exactly that state universally.

**Is the foundation sound?** The *identity* foundation is sound and is the best decision in this layer: an author keyed by the Firebase uid makes "is this me" free in the rules. **`ownerIdFor` has to come out.** SPEC §11 already names author-keyed evaluations as "the intended direction"; this is a decision to take, not a compromise.

## F3 — The overlay is the load-bearing foundation of the two-audience model, and it has no way back

**What the fault is.** `src/data/overlayAdapter.js` merges remote with local, local wins, per document, forever. No version, no divergence marker, no reconciliation, no expiry. It is correct where documents are small and single-purpose. Several of the app's are not.

- **`players` is global truth and the overlay covers it.** `writeDraft` records a pick by mutating the player's registry record (`src/data/draftStore.js:152-196` → `setFactsMany`). For a viewer that is `local.set('players', id, wholeDoc)`, and `overlaid()` (`overlayAdapter.js:116-124`) replaces the whole remote document. A viewer running the play-along draft SPEC §6 promises him therefore **permanently freezes a few hundred shared player records in his browser** — no later correction by an expert to a name, school or matrix score ever reaches him for those players again. The file's own header claims the opposite: "the next read hands back the expert's board with that one placement replaced." That is true of board entries and of nothing else.
- **`prospects_v1`** is one blob per season (`src/data/stageStore.js:41`). One local prospect shadows every expert's added players for good.
- **`draft_state/{seasonId}`** is one blob. Same.

Reconciliation being absent is documented and is a genuinely parked decision (SPEC §11) — fair. But the *consequence* is already shipped, permanent, and invisible: nothing tells a viewer he has diverged, nothing offers "take theirs," and the local half survives every reload.

Two more structural problems in the same file:

- **`writesRemote` is one global, session-mutable boolean** (`src/data/backend.js:57`) routing every write rather than routing per target. So an expert editing a board he may not write is refused-forever (F2's amplifier) rather than routed anywhere, and an unconfirmed expert writes local (F4).
- **`clear(path)` for an expert calls `remote.clear(path)`** (`overlayAdapter.js:278`) — deletes the whole shared collection. Reachable from `clearRegistry()` (`playerRegistry.js:520`) and `seasonStorage.evictSeason`.

**Is the foundation sound?** **The idea is sound; as built it has to come out.** Keep "the viewer writes *over*" — it is the right answer to the asymmetry. It needs three things it does not have: per-collection opt-in (never over `players` or anything that is global fact), a divergence marker plus a "take theirs" path, and write routing decided per target rather than per session.

## F4 — The fix for the demoted-expert shadow copy does not fix it

`src/utils/auth.js:435-453` carries a long comment: on a failed invite check, keeping the session as `unconfirmed` rather than demoting, because demoting means "because a local write wins on read (overlayAdapter.js), every edit he makes afterward becomes a shadow copy that never reaches the shared board."

The code keeps the session and sets `isAllowed: false`. `writesRemote: isExpert` reads `isAllowed` (`auth.js:84-86`, `backend.js:57`). **So every write still goes local. The shadow copy still happens.** `unconfirmed` is consumed in exactly one place — `src/components/SessionUser.jsx:43,82`, a label and a Re-check button — and `editRefusal()` never looks at it, so `canEdit()` is true everywhere for an unconfirmed expert and the app cheerfully accepts a session's worth of work into a private shadow.

This is the pattern rather than the instance: several long, confident comments describe a fix one layer away from the mechanism that actually decides. Three more of the same kind:

- `firestore.rules:123-124` justifies `ownsBoard`'s `!boardExists(boardId)` branch as "so that `create` can function at all." Both call sites guard it with `boardExists` (`:506`, `:200`). The branch is unreachable and the justification is invented.
- `src/data/boardPool.js:22-24` documents `boardFromEntries` as "For the draft board." It has **zero callers** (grep). See F8.
- `src/utils/permissions.js:14-17` still says "Nothing is written today — there is no sign-in yet — so this always answers yes."

## F5 — Boot seeds before sign-in resolves, and the retry duplicates rather than repairs

`src/main.jsx:24-44` does not await `startAuth()` before `createRoot(...).render()`. `openBoards()` runs from `useBoardRankings`/`useDraftState` effects, concurrently with sign-in.

1. Boot: store is empty, `isExpert()` still false → `openBoards()` seeds a season, 3 authors, 3 boards, 3 invites — **all local**, with freshly minted ids (`boardRegistry.js:133-172`).
2. Auth resolves. `main.jsx:36-41` re-runs `openBoards()`. `storedDocs(BOARDS)` reads `overlayAdapter.lastRemote`, which only records *remote* answers, so it is still `{}` → **it seeds again**, remotely, with different ids (`newId` uniquifies against the *merged* cache via `repository.all`).
3. The expert's browser now holds two seasons both `status: 'current'` for the same year and six boards. `currentSeason()` (`boardRegistry.js:197`) picks arbitrarily between them, so half the app is scoped to a season that exists only locally, and stages written under it are orphaned remotely.

The same mechanism gives every viewer who arrives before the external seed a permanent private season alongside the shared one, with no reconciliation (F3).

`ARCHITECTURE.md` §8: "Populating a shared store for the first time is done **from outside the app**… It is not something every client attempts on startup." It still is. The only thing preventing it in production is a CI step that deletes the CSVs from `dist/`, and `.github/workflows/deploy.yml` states this outright:

> "Withholding the files is deliberately the whole mechanism: loadFiles catches a failed fetch and caches null, playerFacts treats an empty body as no rows, and seedBoard does nothing without a pool. **No seeding code changes, nothing to keep in sync with a flag.**"

Three independent silent-failure behaviours are load-bearing as a data-integrity guarantee. And `scripts/build-firebase.sh` does **not** strip the files, so every local Firebase build runs a code path production does not have — meaning local verification of the shared build verifies a different app.

**Is the foundation sound?** **Client-side seeding has to come out.** Replace it with a refusal: if `backendName() === 'firebase'`, `openBoards()` should report an unseeded project, not create one. The guarantee belongs in code, not in an `rm`.

## F6 — Four of the five stages have no ownership model, and the rules make every expert a superuser

`firestore.rules:390-403`, `:312-315`, `:545-548`:

```
match /seasons/{seasonId}      { allow write: if isExpert();
  match /{document=**}         { allow write: if isExpert(); } }
match /players/{playerId}      { allow write: if isExpert(); }
match /draft_state/{seasonId}  { allow write: if isExpert(); }
```

No owner, no author scoping. So any one expert can overwrite any other's roster, free-agency board, draft state, prospect pool and player facts; archive or roll back a season (destroying everyone's boards); and — `email2author` is `allow delete: if isExpert()` (`:299`) with no admin tier — **revoke every other expert, including whoever set the project up.** `revokeExpert`'s self-revocation guard (`auth.js:326-328`) is a JavaScript `if`. There is no rule preventing the last invite from being deleted, which locks everyone out permanently short of the console.

Underneath sits an unresolved product question the architecture never addresses: boards are per-author, the other four stages are singular and global. SPEC says "**your** draft picks and **your** UDFA signings" (§2) and that an expert's changes reach everybody (§6), but never resolves whether two analysts share one roster. The code silently answers "yes, last write wins, no conflict signal" — two people working live clobber each other invisibly.

`writeEntries` makes this concretely worse. `src/data/boardEntries.js:223-232` appends a **whole-board-document overwrite assembled from the local cache** to every entry batch:

```js
const board = repository.get(BOARDS, boardId);
items.push({ collection: BOARDS, id: boardId, doc: { ...board, [ENTRIES_STAMP]: Date.now() } });
```

- A stale cached board clobbers a concurrent visibility or label change (lost update).
- If the cached `o` is stale, `ownershipWouldBeSafe` (`firestore.rules:480`) refuses the **whole batch** — all 328 entries drop into F2's permanent-overlay state.
- It contradicts `ARCHITECTURE.md` §10 directly: "A single change writes a single record — **moving one player does not rewrite a board**."

**Is the foundation sound?** The rules-as-authority principle is sound and the 31KB file is mostly careful. What has to change: a permission tier above "invited" for revocation and season lifecycle, per-author or explicitly-shared scoping for the four non-board stages, and the board stamp written as a field update rather than a whole-document rewrite from cache.

## F7 — Read failures and dead listeners are silent; the one message built for it is unreachable

The broadcast constraint is "must never stall or blank," and SPEC §9 is "A failed save is visible, never silent," §6 "Boards show that they are loading rather than filling in silently." All three fail on the read side.

- **`repository.loadFailed()` has exactly one consumer in the whole app** — `ownerRevokedLocally` (`boardRegistry.js:645`). No UI surface at all (grep). A Firestore read failure returns `{}` (`overlayAdapter.js:88-92`) plus a `console.warn`, and renders as an empty board.
- **The "live updates stopped" message is unreachable.** `repository.js:287-295` builds `advice: 'Live updates stopped. What is on screen is the last the store sent.'` with `permanent: false`. The only listener — `src/App.jsx:124-125` — begins `if (!permanent) return;`. `syncState()` is derived from `pending`/`inFlight` only, so it does not show it either. **A dead listener mid-broadcast is completely silent.**
- **A `permission-denied` on a watch blanks the board on purpose.** `repository.js:280-285` calls `invalidate(collection)` + `notify()`, so subscribers receive `undefined`. The comment argues for it ("Stop quietly and drop the stale cache instead of leaving the last thing he was allowed to see on screen forever"). That is a deliberate choice to blank a live board with no explanation.
- **No viewer can read any author record.** `firestore.rules:356` — `allow read: if isExpert() || authorId == request.auth.uid`. `openBoards()` calls `repository.ready(AUTHORS)` unconditionally, and for a viewer it is refused into a silent `{}`. So `authorOf(board)` returns null for every board for the whole audience: no author on any board, no name to group remarks under. SPEC §3 and §6 require both. (Inferred from the rules plus the code path; not driven in a browser.)

## F8 — "One derivation of who is in this class" is half-applied; the draft still parses the CSV on every boot

Commit `b35b969` is titled "One derivation of who is in this class," and `src/data/boardPool.js` opens by naming the bug: "There were two answers to that question and they disagreed."

`boardFromEntries` — documented at `boardPool.js:22-24` as "For the draft board" — **has zero callers.** Only `castFromEntries` is used, by Scouting. The draft was never moved.

`src/hooks/useDraftState.js:216-256`, on every mount: fetches `rankings_*.csv`, `picks.txt`, `columns.txt` and `DraftBoard_Picks.csv`, then

```js
const poolIds = resolveAll(rawPlayers.map(p => ({ name: p.name, position: p.position, school: p.school })));
```

`resolveAll` defaults to `{ create: true }` (`playerRegistry.js:282`) — fuzzy name matching (Levenshtein, via `findMatchingIndex`) that **mints registry documents**. For an expert those writes land in the shared `players` collection. The project's own CI comment confirms the whole picture:

> "useDraftState builds the Draft and UDFA pool straight from the rankings CSV and has no other source… **Two independent pool builders, one following 'storage is the truth' and one not.** Until the draft is moved onto the same derivation, its file has to be there."

Consequences:

- `ARCHITECTURE.md` §5 — "Shipped files seed the first state and are then irrelevant… not re-read on every start" — is false for four files.
- §8 — "Where the app matches names to people… it does so **once, at the boundary**. Afterwards, everything refers to people by identity, never by name" — is false. It happens on the boot path of every client, and any drift between the shipped file and the registry mints duplicates in shared data. This is the twelve-duplicates bug (BUGS.md line 820) with a live trigger still attached.
- The Draft board's pool is the shipped consensus file, not the board's entries, so app-added prospects never appear on it — against SPEC §4's "otherwise an ordinary player."

`resolveAll` also runs during `writeDraft` (`draftStore.js:167-173`) — minting identity on the on-air pick path.

## F9 — The draft's live-sync effect is wired to its own writes

`useDraftState.js:394-400` opens `repository.follow(PLAYERS, adopt)` and `follow(DRAFT_STATE, adopt)`. `follow` is `subscribe` + `startWatching` (`repository.js:245-247`), and `applyLocal` calls `notify(collection)` on **every local write** (`repository.js:495-502`). So the persist effect (`:404-410`, firing on any of six state values) calls `writeDraft` → `notify` → `adopt` → six setters → persist effect.

It terminates only because `writeDraft` diffs and stops issuing writes (`draftStore.js:191`, `:200-205`). Nothing enforces that invariant. And `adopt` unconditionally replaces `players` with `reconcileDraft(poolRef.current, …)`, where `poolRef.current` is the boot-time CSV pool — so any in-session change to the pool is silently discarded on the next notify, including one triggered by the app's own write.

## F10 — `scrapSeason` is a dozen unsequenced network writes with no atomicity and no verification

`boardRegistry.js:396-424`. Boards and their entries are deleted first (328 deletes per board), the season record last. Any failure in between leaves boards gone and the season alive; a failure after `repository.remove(SEASONS, …)` but before `previous → current` leaves `currentSeason()` null, at which point `createBoard` and `startSeason` both return null and the app has no writable season. Every write is optimistic-local, so it *looks* like it worked regardless of what the store did. SPEC §5 promises "A scrapped season is gone."

Related: `flush()` retries a failed `commitMany` as individual `adapter.set` calls (`repository.js:694-698`), so the cross-collection atomicity `commitMany` exists for is lost precisely on the path that needs it.

## F11 — `ARCHITECTURE.md` §7 is a fully-tested dead subsystem

`src/utils/seasonStorage.js` implements `storageUsage`, `seasonFootprint`, `reachablePlayerIds`, `oldestEvictable`, `evictSeason`. **Zero callers in `src/`.** The only importer anywhere is `tests/unit/seasonStorage.test.js`.

So none of §7 holds: the app does not know what it is using, nothing is evicted, no export is offered before discarding, nothing "acts before it runs out." BUGS.md item 23 measures a genuinely scouted season at 0.5–1.1 MB against a ~5 MB cap — **four to ten seasons** before writes start throwing, at which point they land in the pending queue and `gaveUp`.

The pattern is worth more than the instance: a green test suite over code the app never runs is worse than no tests, because it reads as coverage.

## F13 — Smaller, verified, still real

- `inviteExpert` uses `setDoc` on `email2author`, but `firestore.rules:295` is `allow update: if false`. Re-inviting an already-invited address is a hard permission error. Same for `reinstateExpert` on somebody never revoked.
- `editRefusal` never refuses an orphaned board — `subject.ownerId` is null, so the `if` at `permissions.js:95` is skipped. `ScoutingView.jsx:105` therefore opens an orphaned board fully editable while the rules refuse every write (`tests/rules/rules.test.js:449` confirms they do). SPEC §6: "Orphaned — … nobody can write it."
- `entryDocId` falls back to `identityKey(entry.name, entry.position)` (`boardEntries.js:104`) — a name-derived composite document id, against `ARCHITECTURE.md` §5 ("Identifiers are opaque, short and single. **No composite keys anywhere**") and against the registry's entire reason for existing.
- `rosterSync.isAlreadyOnRoster` and every slot comparison key on the name string (`rosterSync.js:52-55`), against §8's "never by name." Two players sharing a name — which SPEC §3 explicitly permits — silently collapse to one on the roster.
- A remark handle is an **array index** (`{season}:{kind}:{index}`, `evaluations.js:87`) into a document that deliberately does not stream live. An edit from a stale copy deletes the wrong line. The comment acknowledges it and accepts it for a 21% size saving.
- Remarks keyed by a board id are stranded permanently if the board is deleted — `scrapSeason` removes boards and leaves evaluations "deliberately alone," and `ownsVoice` needs `boardExists`, so nobody can ever write them again.
- `boards` is `allow read: if true` (`firestore.rules:408`), so a `private` board's label, author, owner uid and season leak to the world. Documented as intentional in §3; SPEC §6 says "visible to its owner only."
- `stageStore.STAGE_KEYS` still lists `rosterState` and `fa_state_v1`, which moved to `depthChartStore`. `scrapSeason` deletes both ways.
- `scripts/seed-firestore.mjs` claims to avoid drift by "running the app's own code," then reimplements `useDraftState`'s draft-seeding in JS (`:357-360`) because a React hook cannot be called from Node. Two implementations of the draft seed, exactly what the header says it is avoiding.
- BUGS.md "Standing work": "Remaining: a sign-in control, and deploy config." Both exist.
- `.env.local` holds the live project's API key — checked, and it is covered by `*.local` in `.gitignore`, so not committed. Noting only that it was verified.

## Soundness verdict per foundation

| Foundation | Verdict |
|---|---|
| Synchronous reads / async writes in the repository | **Sound. Keep.** The reasoning at `repository.js:9-24` is correct and the board genuinely cannot await a frame. |
| One document per player per board (`boards/{id}/entries`) | **Sound. Keep.** The best-shaped collection in the app; the rule-per-path argument is real. |
| Authors keyed by the Firebase uid | **Sound. Keep.** Makes "is this me" free in the rules. Betrayed by the placeholder seed and by `ownerIdFor`, not by itself. |
| Derived rank, never persisted | **Sound.** SPEC §3 satisfied. |
| Short field names | **Sound.** Cost is that the rules must know them; that bit once and is now documented. |
| Rules as the sole authority | **Sound in principle, needs restructuring.** The "ONE identity read per evaluation, and never two" claim at `firestore.rules:29` is false — an entry write is three accesses, an entries read up to six. §3's "checking several is not acceptable" is violated. |
| Optimistic write + persistent retry queue | **Half sound.** The queue is right. `withPending` laying *permanently refused* writes over reads forever is wrong, and is the amplifier that turns F2 from an error into silent data loss. |
| The overlay adapter | **Idea sound, implementation has to come out.** Per-document merge over collections that hold global truth, with no reconciliation and session-global write routing. |
| The adapter interface (whole-collection `load`/`watch`) | **Has to come out.** Cannot express §4's deltas, which is what §5's budget depends on. |
| Client-side seeding | **Has to come out.** Prevented in production only by deleting files in CI. |
| §4 changed-since markers and deltas | **Not built.** One marker, one consumer, and its delta is a full refetch. |
| §6 relay | **Not built at all.** |
| §7 local budget and eviction | **Not built.** Written, tested, never called. |

## The three worst, and what I would do

### 1. The read budget, and the missing relay (F1)

The deployed shared build supports roughly 25–35 page loads a day for the entire audience before the free tier stops the app for everybody. That is not a tuning problem; it is the product not existing yet.

**Do, in order:** (a) instrument one real boot and count actual billed reads against the live project — publish the number, because every other decision here follows from it; (b) stop subscribing to the whole 728-document registry — the draft needs *names*, not a live stream of every player who ever existed; read the players a board actually references; (c) delete the `usePlayerTags` invalidate-and-refetch (`usePlayerTags.js:111-125`) — it is a second full read of a board already in memory; (d) then decide honestly between building §6's relay and declaring the hosted backend an **experts-only** tool with the audience on the local-only build. Do not ship the current shape to an audience of any size.

Do not build the delta mechanism on today's adapter. The interface has to gain a `since` and per-document stamps first, or the work will be thrown away.

### 2. `ownerIdFor` — evaluations keyed by the board (F2)

Every personal board in the shipped data silently swallows every note anybody writes on it.

**Do:** key remarks on the writer's uid, unconditionally — this is SPEC §11's stated direction, so take the decision rather than continuing to defer it. Drop the board-id case entirely; `ownsVoice` collapses to `ownsAuthor`, which as a bonus removes two `get()`s from the write path. Migrate `evaluations/{p}/remarks/{placeholderId}` → `{uid}` under admin credentials. Stop seeding placeholder authors — seed the shipped personal boards with `a: null` until a real expert claims one, or accept that a board's author must be settable once and add a rule for it. Until this lands, **`withPending` must not overlay a write the store has permanently refused** — that is what converts a visible error into invisible loss, and it is a five-line change in `repository.js`.

### 3. Seeding in the client, plus the overlay's one-way door (F5 + F3)

A CI `rm` is not a data-integrity guarantee, and "local wins forever, silently" is not a sync model.

**Do:** make `openBoards()` refuse to seed when `backendName() === 'firebase'` — surface "this project has not been seeded" instead of creating a private season.
