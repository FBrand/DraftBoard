# DraftBoard `firebase` layer — independent audit, second pass

2026-09-30. Same reviewer as `AUDIT-2026-09-28.md`, resumed against the same
brief: adversarial, structural first, no remedies. Measured against `SPEC.md`
(requirements), `REBUILD-PLAN.md` (the plan and the decisions added to it),
`ARCHITECTURE.md` (proposal) and `CLAUDE.md` (project context).

Scope: `35a7d89..25278ab`, 31 commits. Phases 3, 4, most of 5 and part of 6.

Ran: `npm run test:unit` — **733 passed**. `npm run test:rules` — **109
passed**, against the emulator. Plus a seven-case probe of my own against the
emulator, since several of the questions put to me are rules questions the
existing suite does not ask; it was removed after running. "Measured" below means
it was executed and the result is quoted. "Read" means read and not executed.

Four of the fourteen rotten foundations in the previous report are **closed**,
and one of them — the three-state write model — is the best work in this batch.
Three are **worse than they were**, because two phases built a week apart made
opposite assumptions about the same data. The rest are open.

## 2. Rotten foundations, by structural weight

### R1 — `mine` is a request made at the wrong layer, and the on-air pick path does not make it

The model says: only the lead's picks reach the database. The mechanism is a
`{ mine: true }` flag threaded through `overlayAdapter` → `repository` →
`playerRegistry.setFactsMany`, honoured ahead of the permission question. The
adapter half is correct. The app does not use it on the path that matters.

- `useDraftState.draftPlayer` records the pick with `setFacts(id, {...})`
  (`:485-492`). `setFacts` takes **no options**; `writeOne` is
  `repository.set(PLAYERS, record.id, lean(record))` with nothing after it
  (`playerRegistry.js:96-98`). `signUndrafted` is the same (`:534-535`).
- Nothing in `DraftView`, `CenterBoard` or `TopPanel_Draft` gates picking on
  holding the lead. `LeadControl` claims, releases, and displays.
- **Measured** against the emulator, with Dan holding the lead: Ryan is refused
  the draft document, and `setDoc(players/p_1, { dp: 4, ty: 'KC', dy: 2026 })`
  **succeeds**. The rules cannot tell a pick from a school correction and say so
  in their own comment; the app was supposed to. It doesn't.
- `writeDraft`'s `privateDraft()` is then dead for picks by construction. It
  diffs `factsFor(id)` — the *merged* view — and `setFacts` has already put the
  facts there synchronously, so `DRAFT_FACTS.every(...)` finds no change and
  `setFactsMany(updates, { mine })` is never reached with a pick in it.
- Three more unmarked writers on the same collection: `resolveAll`
  (`playerRegistry.js:282`, options are `{ create }` only) mints a shared player
  document for any UDFA signing the registry has not seen;
  `recordDraftFacts` (`useDraftState.js:105`) calls `setFactsMany(updates)` bare;
  `draftStore.removeDraft` calls it bare, so scrapping a season nulls the draft
  facts of every drafted player in the shared registry with no lead check.
- The flag **cannot be expressed** through `docSet`
  (`repository.commit(collection, changes)`, no opts — so no chart row, board
  entry or prospect can ever be private) or through the new contract
  (`Change` has no `mine`; `fromLegacyAdapter.write` drops it). Two of the app's
  three write paths cannot carry the intent the whole model rests on.

`tests/unit/privateDraft.test.js` builds an overlay over two memory adapters and
asserts the adapter honours the flag in all four methods. It never asserts that
the app sets it. `draftLead.test.js` drives `writeDraft` directly. So the plan's
own Phase 4 gate — "a second expert's picks do not reach the database" — is not
met, and no suite in the repository looks at it.

**Why it is structural, not a bug.** "Only the lead writes" is stated as a
property of the call graph. It has no representation in the data, no
representation in the rules, and no single choke point in the app — three
independent code paths write the same collection and each has to remember. The
commit message names this exact failure mode ("an easy thing to thread through
and get silently wrong") and then tests the half that was easy.

### R2 — The private overlay has no way back, and now holds global facts on purpose

`mine: true` routes to `local.set` — localStorage — and `overlaid()` gives the
local document absolute, permanent, per-document priority over the shared one.
Nothing records *which* documents are private, so nothing can distinguish an
expert's deliberate private pick from a viewer's play-along from a stale shadow.

- **An independent expert who later claims the lead publishes nothing.**
  `writeDraft` diffs against the merged view; his own overlay already says
  drafted; no update is issued. Screen full, database empty — the same shape as
  the last report's F2, arrived at from the opposite direction.
- The only path that removes an overlay document is `overlayAdapter.clear(path)`,
  and for an expert that is `remote.clear(path)` — `firebaseAdapter.clear` lists
  the collection and deletes every document in it. There is no expert-safe
  discard. (`clearRegistry` now has no callers, which narrows the reach;
  `seasonStorage.evictSeason` still calls it and has no callers either.)
- Phase 5 then contradicts Phase 4 outright. `storageBudget.EVICTABLE` lists
  `players`, with the reason "The shared store has all of this; the local copy is
  a cache." For an independent expert it does not: `mine: true` put it there
  precisely so the store would **not** have it. Two phases, one week apart, with
  opposite claims about the ownership of one localStorage key.
- `REBUILD-PLAN.md` §5: "**The private scope is opt-in per collection and never
  covers global facts.** The registry is shared truth." The mechanism that
  section specifies covers `players`, which is the global-fact collection. The
  prohibition and the design are in the same section.

### R3 — A chart's storage address embeds an identity that arrives later than the read

`myScope() = repository.identity() ?? 'local'` (`depthChartStore.js:71`),
evaluated as a default argument at call time and baked into
`seasons/{s}/charts/{stage}/scopes/{whose}/rows`.

- `main.jsx` does not await `startAuth()`; the tree renders first, deliberately.
- `useBoardRankings.loadPools` (effect deps `[gen, allBoards]`) and
  `useDraftState.loadInitialData` (deps `[]`) both call
  `openDepthCharts(season)` at t=0, when `repository.identity()` is null. Scope
  is the literal string `local`.
- **Measured:** writing `seasons/s_1/charts/rosterState/scopes/local/rows/QB` as
  an expert is refused — `false for 'create' @ L461`. So a pre-auth chart write
  is a permission error and a pre-auth chart read opens a collection that can
  never hold anything on a shared store.
- Nothing re-derives the scope when the session lands. `loadPools` does not
  depend on auth. `RosterView` re-opens on its own mount — but the view is
  restored from localStorage (`App.jsx:76-78`), so an expert whose last tab was
  Roster mounts it before the session arrives: `readFrom(stage, sid, 'local')`
  finds nothing of his, falls through to official, `loadState()` answers with
  official or nothing, and `shouldSeed()` then seeds from the shipped file or the
  season-start structure into `history.reset(loaded)`. His first save writes that
  over his own scope.
- `hasOwnChart` is false for the same reason, so `OfficialBar` tells an expert
  who *has* a personal roster in the store that he is "Showing the **official**
  roster — your first change makes it yours".

Commit `cb8d590` is titled "Boot does not race sign-in" and is correct about what
it tested: the board **visibility filter** asks the current identity at render
time, so it converges. A path is not a filter. It is written once and cannot be
re-asked, and no test covers a personal chart across a cold load.

### R4 — The durable watermark persists the point without the data, which is the state the same file exists to prevent

`recallMarks()` (`store.js:87-97`) restores `at` with `answered: false` and an
empty `shared` map. `ready()` sends it as `since`. A delta-capable backend
answers `complete: false`, and `absorb` merges the delta onto
`shared.get(collection) ?? {}` — i.e. onto nothing. The collection then holds
the handful of recently-changed documents and reports `answered: true`.

`forget()`, 200 lines below, documents this exact failure and drops the watermark
with the documents: *"Keeping it would leave a point in time with nothing behind
it, so the next read would ask for what changed since then and rebuild a
collection out of a handful of recent changes — an emptied cache presenting
itself as a current one."* Two functions in one file give opposite answers to
one question.

It is inert today only because `fromLegacyAdapter.read(collection)`
(`contract.js:180-183`) does not accept `since` at all and always reports
`complete: true`. So the durable watermark buys **zero** reads now — against a
commit message claiming it "separates roughly 3,000 reads a day from 30" — and
becomes wrong at the moment Phase 6 builds the delta it was written for.

`durableWatermark.test.js:46-57` constructs a fake whose delta *is* the whole
collection and never asserts what `shared()` contains after the second read. The
mechanism is pinned; the outcome is not. Also `readSync` stamps
`String(Date.now())` — a client clock — and that value is persisted as a
watermark and would be sent to a store that does not share the clock.

**The answer to the question as put:** the split is not correct. The point and
the documents are one fact. Persisting half of it is not conservative.

### R5 — The lead can be claimed but not reclaimed: a revoked or absent lead freezes the live draft

**Measured.** `draft_state/s_1 = { o: 'dan-uid', value: {...} }`, then Dan's
`email2author` entry deleted (which is what revocation *is* in this design):

```
Ryan claims it                       REFUSED
Ryan writes it, leaving o alone      REFUSED
Ryan deletes it to start again       REFUSED
Dan releases it                      REFUSED  (he is no longer an expert)
```

The same board state **is** recoverable — measured: Ryan writes
`boards/b_dan { o: 'ryan-uid' }` and it succeeds, because `boards` carries a
third carve-out gated on `ownerRevoked(resource.data.o)`. The rules explain that
carve-out at length, in the file, immediately above, naming the lockout it
prevents. `draft_state` was given the same field, the same shape and the same
claim/release grammar, and not the carve-out.

Two further properties of the same choice:

- There is deliberately no way to take the lead from a holder. On air that is
  one closed laptop between the show and an unwritable draft; only the holder can
  release, and only while he is still invited.
- **Two browser tabs as the same expert are both the lead.** Both satisfy the
  rules, both answer `iAmLead` true, and both write the draft document whole —
  `writeDraft` assembles it from cache (`const kept = before?.o === undefined ?
  {} : { o: before.o }`, then `repository.set`, a full replace). Last write wins
  with a copy that never saw the other. That is the whole-record-from-cache
  pattern commit `6b3c2b5` removed from `boardEntries` **one commit earlier**,
  reintroduced in the next. A stale cached `o` is also written back and refused.

"Exactly one writer" is one uid, not one session.

### R6 — `adoptOfficial` loses the players it does not look at

`playersNotIn(from, to)` (`officialVersion.js:46-62`) scans `from.depthChart`
only. `adoptOfficial` then calls
`saveState({ ...official, cuts: [...official.cuts, ...displaced] })`, which
replaces the whole state — so `mine.reserve` and `mine.cuts` become official's.

Anybody on the adopter's **injured reserve** whom official does not carry is
therefore neither kept nor cut. He is gone. His own cut list goes the same way.
`countDisplaced` undercounts by exactly that set, so the confirmation dialog
states a number lower than the real loss and says nothing about the rest.

`SPEC.md` §6: "Anybody you had who is not in it goes to the **cut panel** —
never simply gone. That is the whole difference between adopting a state and
losing an afternoon's work." The one version of this that the plan says must not
ship — players disappearing with nothing saying which — ships for the reserve
zone. The suite that caught the first `playersNotIn` bug compares depth-chart
slots and does not build a reserve.

Adoption is also a multi-document optimistic write with no atomicity, no
verification and no undo. **Nothing here is unlosable.**

### R7 — Nothing enforces who may publish, adopt, seed a season or scrap one

- `canPublish={canEdit({ kind: 'stage' })}` (`RosterView.jsx:631`,
  `FreeAgencyView.jsx:372`). `editRefusal` refuses only an archived season or a
  mismatched `ownerId`, so this is **true for a viewer**. "Make official" is
  offered to the whole audience; his publish writes `scopes/official` into his
  own overlay, where it permanently shadows the real official chart while
  `isOwn()` keeps telling him he is looking at official.
- `SeasonModal` has **no expert gate at all**. A viewer can Roll Over — creating
  a private season that wins on read, which is precisely the failure the seeding
  gate was built to close, reachable from a button — and Roll Back, where
  `scrapSeason`'s `repository.remove` calls become local tombstones over the
  shared season, its boards, its entries and its charts. Tombstones are
  persisted and survive reloads; `overlaid()` drops the document on the way out.
  There is no way back short of a clear.
- `editRefusal` still takes `{ ownerId, kind }`. `REBUILD-PLAN.md` §5 names
  widening it as part of Phase 4 — "It takes the board's actual state" — and
  Phase 4 is committed as *finished*. So an orphaned board still opens fully
  editable (`ScoutingView.jsx:105`, `subject.ownerId` is null) while every write
  to it is refused.
- Rules-side, Phase 7's absence has stopped being merely pending. **Measured:**
  one expert deletes another's `email2author` entry and it succeeds; nothing
  prevents the last one going. Combined with R5, revocation now has a second
  irreversible consequence nobody chose.

### R8 — Two stores, and the newer seam cannot express the newer write model

`repository` serves everything; `store` (`appStore.js`) serves `evaluations`.
Two caches, two refusal models, two readiness models, and only one of them has a
watermark. The rule that keeps them apart is a hand-maintained list.

`contract.js`'s `Change` and `fromLegacyAdapter.write` have no room for `mine`,
and `store.write` drops write options entirely. So the seam Phase 2 built as the
future cannot carry the intent Phase 4 built two phases later: every collection
that crosses loses the ability to hold private work. The two phases were
designed in sequence and do not compose.

`store.ready` also re-reads unconditionally — the bridge ignores `since` — and
`shared` is never evicted. So remarks are simultaneously **re-read on every card
open** and **resident forever**, which are the two things §6 says must not both
be true. (I am not reporting "remarks are not resident" as missing; I am
reporting that the mechanism standing in for it has neither of its properties,
and that `ARCHITECTURE.md` §4's "without paying to re-read what has not changed"
has no marker on remarks to make it possible.)

### R9 — Both new budget instruments measure the wrong quantity, and one assertion cannot fail

- **`readBudget.test.js` counts collections opened, mocking `repository.ready`
  so nothing is read.** Firestore bills documents. The three board-entry
  collections in its count are roughly 984 documents; the player registry — the
  largest single item and the one the previous report priced at 728 — is not in
  the list at all, because `openRegistry` goes through `readyVia` and
  `openDraft`'s `readyVia(PLAYERS)` is not on this path. The commit presents
  "19 collections" as an update to "~1,484 documents". They are not the same
  measurement, and the number that is billed is the one not taken.
- **`localBudget.test.js` asserts a tautology.** It builds a dump containing
  only `evaluations/...` paths and then asserts
  `expect(top[0]).toBe('evaluations')` — over its own input. The comment says
  the assertion exists so that "if something else ever does, the budget work is
  aimed at the wrong thing"; it cannot detect that. It also weighs
  `store.view()` rather than what the local adapter stores, explicitly because
  the memory adapter loses concurrent writes — so the figure is for an idealised
  shape, not for a browser, and excludes the registry, the board entries, the
  charts and the prospects entirely.
- **`usePlayerTags`' stamp gate is per-mount, not per-change.** `seenStamp` is a
  `useRef` inside the hook; `App.jsx` renders one view at a time, so DraftView
  unmounts on every tab switch and the ref resets. Entering the Draft tab costs
  a full 328-document re-read of the board whether or not it changed. The
  unconditional re-read the last report flagged was replaced by one that is
  conditional on session memory that does not survive the session.
- **`utils/storageBudget.js` has zero callers in `src/`.** `measure`,
  `biggest`, `byCollection`, `evictionPlan` — all written, all measured by a
  test, none reachable. This is A23/F11 again, in a new module, one phase after
  the plan named the pattern. `evictionPlan`'s comment describes "a dialog that
  has to tell somebody why his roster is about to stop saving". There is no such
  dialog. Phase 5's gate — "the local build refuses to lose data without an
  export" — cannot be met, because nothing in the app can refuse anything.

### R10 — Boot still mints identity into shared data by fuzzy name match

`useDraftState.loadInitialData` fetches the rankings CSV on every mount and calls
`resolveAll(rawPlayers.map(...))` (`:263`) with the default `create: true` —
outside the `shouldSeed()` gate, unconditionally, on every boot. For an expert
those writes land in the shared `players` collection, unmarked.

`.github/workflows/deploy.yml` keeps the rankings files in the shared build
deliberately, and argues: *"This does NOT reopen the seeding hole, because
seeding is gated on the DATA and not on the file."* That is true of `seedBoard`
and `loadFiles`. It is not true of `resolveAll`, which is not gated on anything.
So every expert's boot fuzzy-matches ~328 names against the shared registry and
mints a document for each miss — the twelve-duplicates bug with a live trigger
still attached, now on the shared store.

`scripts/build-firebase.sh` still strips nothing, so the local emulator build
runs a code path the deployed build does not. Local verification of the shared
build still verifies a different app.

### R11 — No viewer can resolve any author, and a comment now asserts that none needs to

**Measured:** an anonymous viewer and an unauthenticated reader are both refused
`authors/dan-uid`, and both may read `evaluations/p_1/remarks/dan-uid`.

`PlayerInfoModal.allVoiceNotes` (`:223`) labels every voice
`authorById(voiceId)?.name ?? 'Unattributed'`. The player card is viewer-facing
by `SPEC.md` §3 ("Opens from anywhere outside Scouting… It shows **every**
evaluation of that player, from every author… grouped under the author's name").
So for the entire audience, every remark by every analyst renders as
**Unattributed**.

`firestore.rules:349-353` asserts the opposite, in a comment written to justify
the restriction: *"Nothing viewer-facing needs an author… `authorOf()` has no
caller outside the tests. Every real consumer… is expert-only already."*
`authorOf` indeed has none. `authorById` does — and it was given one by commit
`2666330`, the commit that made remarks author-grouped in the first place. The
justification was written before the consumer existed and has not been re-checked
since.

`REBUILD-PLAN.md` §2 lists this as a Phase 1 item ("**The audience cannot read
`authors` at all**… This is both a rules defect and the clearest instance of why
read failure must be visible"). Phase 1 is committed as done.

### R12 — Charts carry no visibility, and the rules make every personal roster world-readable

**Measured:** an anonymous viewer and an unauthenticated stranger both read
`seasons/s_1/charts/rosterState/scopes/dan-uid/rows/QB` successfully. The rule is
`allow read: if true` on `charts/{stage}/scopes/{scopeId}/{document=**}`.

`SPEC.md` §6: "A personal roster is visible to its owner only, to experts, or to
everybody, chosen the same way a board is and defaulting the same way **so there
is one model rather than two**." Nothing stores a chart visibility, nothing reads
one, and no rule could honour one. Boards got `boardVisible()` with six branches
and a measured account of two Firestore evaluation traps. The stage that was
added specifically to make the model uniform got none of it, and Phase 4 is
committed as finished.

The same rule has a second consequence worth naming: `readFrom` falls back to the
legacy unscoped path, which stays writable by **any** expert. Keeping it writable
for the deployed older build is defensible; the fallback means whatever is there
is the starting point for every expert who has neither his own chart nor an
official one. Nothing in this build writes it. Nothing stops a build that does.

### R13 — A scrapped season is not gone, and now cannot be

`removeChart(stage, seasonId, ALL_SCOPES)` clears three scopes: this person's,
`official`, and the legacy path. Its own comment concedes the rest: *"Another
expert's personal chart for a purged season outlives the season; it is
unreachable rather than wrong, and enumerating scopes would mean a collection
listing on every rollback."* So every other expert's roster and free agency for a
deleted season stay in the database under a season that no longer exists.

`SPEC.md` §5: "A scrapped season is gone." `scrapSeason` also remains a dozen
unsequenced optimistic writes with no atomicity and no verification, and now
additionally nulls draft facts across the shared registry with no lead check
(R1). The scope model made an already-unsound lifecycle operation incomplete by
construction rather than by accident.

### R14 — Residuals on otherwise sound work

- **Refusal handling.** `repository.js:750-754`: on a permanent refusal the cache
  is rebuilt as `withPending(collection, fromStore.get(collection))` — *if*
  `fromStore` has an answer. When the store never answered for that collection,
  `held` is undefined, the branch is skipped, and the optimistic value stays in
  the cache. That is exactly the case the mechanism is for: a write to a
  collection whose read failed or never ran.
- **`retryNow()`** moves every refusal back into `pending`, and `withPending`
  merges `pending` into reads — so pressing "Try again" re-displays refused work
  as stored until the store refuses it again. Correct as a retry, transiently
  the behaviour the commit removed.
- **`repository.js:84`** — `pending.forEach(lay); // refused, waiting to be
  retried`. `pending` is no longer where refusals live; that is the point of the
  commit above it.
- **F4 is unchanged.** `auth.js:451` still keeps a failed invite check as
  `shape(user, current?.isAllowed ?? false, true)`. For a session that was never
  confirmed, `isAllowed` is false, `writesRemote` is false, and every write goes
  local — the shadow copy the long comment above it describes preventing.
  `editRefusal` never looks at `unconfirmed`, so `canEdit()` is true everywhere.
- **`useBoardRankings.js:206`** calls `openEvaluations()` with no argument.
  `playerIds == null` means `ids = []`, so it loads nothing by construction: a
  no-op in the boot chain.
- **`stageStore.STAGE_KEYS`** still lists `rosterState` and `fa_state_v1`, which
  moved to `depthChartStore`, and `prospects_v1`, which is now three collections.
  `writeStage` is exported and has no callers.

## 3. What the rules audit found, as asked

**No gap between experts on the scoped chart path.** Measured both directions,
both stages: Dan cannot write Ryan's scope, Ryan cannot write Dan's, either may
write `official`, a viewer is refused everywhere including his own scope. The
wildcard removal is correct and the union trap is understood — the exact-match
`charts/{stage}/rows/{rowId}` and `bands/{bandId}` rules, rather than
`{rest=**}`, are the right shape and the reasoning given for them is right.

**One collection the app writes is unreachable:** `scopes/local`, written during
the pre-auth window (R3). Measured refused. `rulesCoverage.test.js` reports it as
covered, because coverage asks whether *some* rule matches, not whether it grants
— and the path it checks is built by `rowsPath(...)` with the same
`myScope()` default, so the test exercises the broken address and passes.

**Over-grants that remain**, in order of weight:

## 5. What I could not determine

- **Whether the pre-auth `scopes/local` window actually destroys a stored
  personal chart in a real browser.** The code path is unambiguous and the rules
  refusal is measured, but the outcome turns on auth latency against
  `RosterView`'s mount, and I cannot settle that without driving a browser
  against the emulator with a personal chart already seeded. The shared
  Playwright suite does not cover a personal chart across a cold load. This is
  the single highest-value thing to measure next, because it is the difference
  between R3 being a wasted read and R3 being silent data loss on every reload.
- **The real document count of a cold Firestore boot.** `readBudget.test.js`
  does not measure it (R9) and I did not drive a live project. The previous
  report's ~1,484 is neither refuted nor updated, and Phase 6's gate asks for a
  counted number against the live project.
- **The real localStorage footprint of a ten-expert season in a browser.** Only
  the in-memory shape is measured, and `measureDump` models one-key-per-collection
  serialisation rather than reading a quota.
- **Whether `firebaseAdapter.commitMany`'s `merge` flag survives a batch split
  above 500 documents.** `adapter.test.js` covers batching and merge separately,
  not together; the board stamp now rides on a merge item inside entry batches
  that can exceed the limit.
- **Whether two tabs of one expert interleave destructively in practice.** The
  rules permit it and the write is a whole-document replace; I did not run it.
- **Whether the `authors` read refusal is visible anywhere.** A refused read
  returns `{}` and the card shows "Unattributed", which is a plausible label for
  a placeholder author — so a viewer cannot distinguish "no author record" from
  "not allowed to look". `repository.loadFailed` still has one consumer.

## 6. Process note, since the same cause is under R1, R3, R9 and R11

Every one of those four is a **correct mechanism with a comment asserting a
property the mechanism does not have**, and in three of the four the comment was
written before the consumer that falsifies it existed. `firestore.rules` asserts
nothing viewer-facing needs an author, and one commit later something does.
`privateDraft`'s test file names the exact failure mode it does not test.
`localBudget`'s assertion names the shape change it cannot detect. `store.js`
contains both halves of a disagreement about watermarks.

The previous report's process note said the comments should be read as a
specification of what somebody meant. That still holds, and there is now a
sharper version of it: **in this codebase a comment justifying a restriction is
the least reliable kind**, because it is written at the moment the restriction
looks obviously right and is never revisited when the thing it excluded acquires
a caller. Four of the five findings I would act on first were found by taking a
confident comment and grepping for the caller it said did not exist.
